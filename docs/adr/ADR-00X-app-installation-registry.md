# ADR-00X: Application Installation Registry

## Status
Accepted

## Context

Hekatoncheiros is an extensible platform that supports applications developed in separate repositories, potentially by third parties.
Applications are not part of the core codebase and must be treated as external components.

An earlier approach relied on a static `app-registry.json` file located outside the core repository, including relative paths to application repositories.
This created tight coupling between core and apps, violated separation of concerns, and prevented safe runtime installation.

## Decision

1. Application registry data is runtime state, not source code.
2. Core must not reference specific applications or their repository structure.
3. Core accesses installed applications exclusively through an abstract `AppInstallationStore`.
4. Application manifests are collected, validated, and normalized during installation.
5. Application installation is a separate process (e.g. marketplace or installer wizard).
6. All core subsystems (proxy, navigation, privileges) use the same installation store as the single source of truth.

## Consequences

- Clean separation between core and applications
- Support for third-party apps
- Runtime install and uninstall without code changes
- No filesystem or repository coupling

## Temporary Dev Installer API (MVP)

During early development, a thin dev-only installer UI is allowed to call core APIs
that write to the in-memory `AppInstallationStore`. This is **not** the final installer
workflow and will be replaced by the marketplace / wizard.

This MVP shape is a development convenience and MUST NOT be treated as the
reference production distribution model for UI plugins.

### Endpoints (v1)

- `GET /api/v1/apps/installed`
- `POST /api/v1/apps/installed`
- `DELETE /api/v1/apps/installed/:app_id`

### Install payload (MVP)

```json
{
  "app_id": "app_inventory",
  "base_url": "http://127.0.0.1:4010",
  "ui_url": "http://127.0.0.1:4011/plugin.js",
  "manifest": { "...": "..." },
  "required_privileges": ["inventory.read"]
}
```

`ui_url` in this MVP example is illustrative only. In the production model,
core MUST own UI plugin artifact storage and runtime exposure, and `ui_url`
MUST be generated by core after installation.

## Security: Installer Identity (UI Artifact Installer Channel)

This section extends the UI plugin distribution model with a security contract
for app-hosted artifact source endpoints.

### Installer Identity

- **Installer Identity** is a system-level service principal represented by
  core for installation-time operations.
- An app-hosted UI plugin artifact source endpoint MUST NOT be publicly
  downloadable without authorization.
- UI plugin artifact fetch from an app backend MUST use an installer-only
  channel (`core -> app backend`) under Installer Identity.
- The web shell MUST NOT fetch UI plugin artifacts directly from the app
  backend.

### Manifest declaration model (conceptual)

- An app MAY declare the UI plugin artifact source as
  `integration.ui.artifact.url`.
- `integration.ui.artifact.url` MAY be either:
  - relative to `base_url` (app backend), or
  - an absolute HTTPS URL.
- For app-hosted artifacts, the app MUST declare
  `integration.ui.artifact.auth = "core-signed-token"`.
- For external artifact sources (for example GitHub or CDN):
  - artifact auth mode does not apply,
  - source URL MUST be HTTPS,
  - artifact integrity MUST be declared (sha256 or signature).
- The manifest MUST NOT define runtime hosting location.
- Runtime `ui_url` MUST be generated by core after installation.

### Installer enforcement (normative)

Core MUST verify all of the following during installation:

1. Request to app-hosted artifact endpoint **without** installer auth MUST
   return `401` or `403`.
2. Request to the same endpoint **with** a valid core-signed installer token
   MUST return `200`.
3. If integrity is declared (sha256/signature), integrity MUST be verified;
   integrity failure MUST reject installation.

If condition (1) or (2) is not satisfied, installation MUST be rejected as a
misconfigured app.

### Installer token model (MVP contract)

- Installer token MUST be short-lived and signed by core.
- Installer token claims MUST include:
  - `app_id`
  - `slug`
  - `tenant_id` (if relevant)
  - `purpose = "ui-artifact-fetch"`
  - `exp`
  - `nonce`
- App backend MUST verify token signature, token purpose, and expiration.
- Without a valid installer token, the app backend MUST return `401` or `403`.

### Future hardened mode (non-goal)

- mTLS is an allowed future hardened alternative for installer-channel
  authentication.
- This ADR does not define mTLS implementation details.

### Privilege

- `platform.apps.manage`

## Rejected Alternatives

- Static app registry files committed to a repository
- Relative filesystem references to application repositories
